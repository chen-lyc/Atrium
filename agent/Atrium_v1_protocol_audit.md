# Atrium 上下文工程 v1 —— 协议核对与纠错文档

## 0. 本文档的用途

v1 已实现。本文档不是新需求,是**协议核对清单**:列出 v1 必须严格满足的不变量(invariant),用于对照现有代码纠错。每条不变量附【违规判定】和【自查方法】。

实现细节(命名、索引、缓存策略、具体参数)由你根据代码现状自行判断,不在协议范围内。判定优先级:

- 标【协议】的条目:违反即为 bug,必须改。
- 标【实现建议】的条目:方向必须遵守,具体方案你有裁量权。

---

## 1. 数据结构

**INV-1【协议】物理分表。**
对话轴(共享白板):主键 `conversation_id`,一对一,不含 ai_id。
立场履历:主键 `(conversation_id, ai_id)`,一对多。
违规判定:两类数据合在一张表;对话轴含 ai_id 维度;履历缺 ai_id 维度。
自查:看 schema。

**INV-2【协议】对话轴字段完整性。**
必须包含:当前目标、已确认约束、已做决策、被否方案、未解决问题、当前方向、阶段标记。
阶段标记为三值枚举:`发散期 / 收敛执行期 / 撞墙期`。不允许其他值,不允许自由文本。

**INV-3【协议】被否方案的条目结构。**
每条被否方案必须是结构化四元组:`{方案内容, 否决理由, 否决时前提, 出处消息 ids}`。
"前提"是独立字段,不允许混进否决理由的自由文本里。
出处消息 ids 是因果链的第三条腿,必须在起草/确认时记录;事后无法可靠重建。
背景:前提字段与出处锚点都是 v2 的承载点,现在混写成散文或丢失锚点,v2 必返工。
自查:看被否方案的存储结构里是否存在独立的 premise 字段和 sources/source_message_ids 字段。

**INV-4【协议】立场履历语义 append + 溯源排除口。**
正常路径只允许追加,不允许更新、重写、抽取已有条目。条目内容 = 该 AI 每轮发言原文或简单摘要。
唯一合法删除/排除口:owner 发起的 provenance / lineage 溯源清除。清除语义默认是"排除后续 prompt 注入 + 保留审计墓碑",不是物理删除;若未来涉及隐私合规硬删除,另行定义物理删除策略。
违规判定:存在非 owner、非溯源清除的 UPDATE / DELETE / 覆盖履历行路径;或 owner 清除后污染履历仍会进入第(4)段。

---

## 2. 拼装层(每轮为某个 AI 构造上下文时)

**INV-5【协议】五段顺序,从前到后严格为:**

1. 静态前缀:common prompt + 模型 adapter + 该 AI 的 thinking adapter
2. 对话轴共享白板(仅已确认内容,见 INV-11b)
3. 最近 N 条原文消息
4. 该 AI 自己的立场履历 + 机制一实例化指令
5. 当前用户消息

违规判定:顺序不同、段落缺失、或第(4)段被放到靠前位置。

**INV-6【协议 · 最高优先级】私有证据位隔离。**
第(4)段的立场履历,查询键必须且只能是 `(conversation_id, 当前回复者的 ai_id)`。任何 AI 的拼装上下文中,绝不允许出现其他 AI 的立场履历。
理由:第(4)段是"私有证据位"。隔离理由是模板位置先验,不是身份定义:这里的内容紧贴当前消息,会被模型读作与当前回复者自身历史相关的证据。B 的履历进了 A 的私有证据位,A 会把 B 的历史判断当成自身历史证据,形成 cross-AI anchoring。
自查:定位拼装函数中的履历查询,确认 ai_id 参数来源是"当前回复者",且不存在任何查全表或查他人的分支。

**INV-7【协议】消息窗口不做跨 AI 过滤。**
第(3)段包含本对话所有参与者(人类 + 所有 AI)截至本轮 t=0 的消息,**不得过滤掉其他 AI 的历史发言**。
理由(防止误实现):Form A 的隔离语义是"同轮并行的 AI 互相看不到彼此本轮的输出",不是"AI 之间看不到对方的历史"。讨论必须互相听见;需要隔离的是私有证据位(INV-6),不是消息流。
违规判定:第(3)段的查询里存在按 ai_id 排除其他 AI 消息的逻辑。

**INV-8【协议】机制一按阶段实例化。**
第(4)段末尾的实例化指令由模板生成,模板按当前阶段标记三选一;槽位取值:
发散期 → 当前目标;收敛执行期 → 最新决策 / 当前方向;撞墙期 → 被质疑的决策 + 其前提字段(INV-3)。
违规判定:只静态注入"你是激进型"之类的人格描述;模板不随阶段切换;槽位取错来源。

**INV-9【实现建议】履历注入截断。**
存储全量 append(INV-4),但拼装注入时需截断(例如:首条 + 最近 K 条,K 由你定)。
全量注入是缺陷:履历体积随轮数增长,会稀释紧随其后的实例化指令。

**INV-10【实现建议】静态前缀字节级稳定。**
第(1)段在整场对话内不应有任何字节变化(KV cache 前提)。任何动态内容一律不进第(1)段。

## 3. 更新层

**INV-11【协议 · 本次新增决定】决策区写入流程。**
三步:AI 起草摘要 → owner 编辑/确认 → 提交写入。约束:

a. 不经 owner 确认环节的决策区写入路径 = 违规。
b. 草稿(未确认)状态必须与已确认数据隔离存放;草稿绝不进入任何 AI 的拼装上下文,只有 owner 确认后的内容才出现在第(2)段。
c. 普通 AI 发言不走审批;审批只适用于边界动作:写白板、切阶段、工具/资源、流程状态变更。
d. 草稿/提案必须记录 `base_phase` 和 `base_context_updated_at_ms`;确认时若基线过期,必须提示 owner 或要求重新确认。
e. 决策区范围:已做决策、被否方案、阶段标记(阶段另见 INV-13)。

自查:列出所有写决策区字段的调用点,逐个确认上游存在 owner 确认动作。

**INV-12【协议】现状区自动维护边界。**
"只记录讨论进展"的字段(未解决问题、当前议题)允许系统自动维护;任何"需要判断对错 / 作废 / 采纳"的内容不允许自动写。判别原则就是这一句,具体字段归属由你按此原则核对。

**INV-13【协议】阶段切换唯一入口。**
修改阶段标记的代码路径必须有且只有一条,触发者必须是 owner 的显式操作。不允许任何定时器、AI 输出、启发式规则修改阶段。
自查:grep 阶段字段的所有写入点。

**INV-14【协议】履历追加时机。**
只有 AI 产生可见发言并落库成功后,才追加一条履历。
`<NO_REPLY>` 是合法沉默:不生成可见消息、不追加履历、不触发链式传导。
追加必须携带 provenance:至少包括 `trigger_message_id`、`response_message_id`、`phase_at_generation`、`context_until_message_id`、`input_stance_record_ids`。
违规判定:沉默产生履历;失败/空回复产生履历;履历缺少触发消息或生成时上下文 watermark;只按 `trigger_message_id` 清第一跳而无法清除被第(4)段回灌污染的后代履历。

## 4. 禁止项(v1 范围外,实现里出现即删)

- **P-1** 系统级实时交叉纠错层(自动冲突检测、自动状态写入、自动仲裁)。不约束任何 AI 在普通发言里指出前文问题。
- **P-2** RAG / 向量召回作为记忆通道。
- **P-3** 决策区的任何自动写入。
- **P-4** AI 自主发起"进入拍板 / 切换阶段"的触发。AI 可以被授予拍板的执行权,但"宣布进入决策"的触发必须来自 owner。

---

## 5. 核对顺序

按风险从高到低:**INV-6 → INV-17 → INV-11 → INV-13 → INV-18 → INV-19 → INV-7 → INV-5 → INV-8 → INV-3 → 其余**。
前三条任何一条违规都是结构级错误,优先修。

---

## 6. v1.5 可选项(非纠错范围,不阻塞,有余力再做)

- **O-1 阶段切换提议信号**:AI 输出中允许携带结构化提议标记(如"建议进入收敛期"),仅展示给 owner,不写任何状态。触发权仍在 owner,不与 INV-13 / P-4 冲突。
- **O-2 差异度展示**:同一轮各 AI 输出之间计算 embedding 距离,仅展示给 owner,不触发任何行为。

# Atrium 上下文工程 v1 —— 协议增补页(文献调研落点)

## 0. 本页的用途

本页是《v1 协议核对与纠错文档》的增补,依据 2026-06 多轮文献调研(多智能体趋同 / 谄媚性 / 人格漂移 / 异构混合 / 记忆投毒 / 人类监督退化)。编号续主文档。判定标准同主文档:【协议】违反即 bug,【实现建议】方向必须遵守、方案有裁量权。

本页不推翻双轴、五段顺序、两区拆分、阶段状态机;但补上 v1 原先缺失的生命周期和威胁模型边界。记忆投毒把"立场履历"从普通连续性机制提升为可信计算基的一部分,必须按安全边界处理。

---

## 1. 对既有条目的修订

### INV-7 增补【协议】消息渲染的角色位约束

原条目要求:消息窗口不做跨 AI 过滤。增补两条:

a. **角色位**:其他参与者(其他 AI、其他人类)的消息,必须渲染在模型明确读作"他者发言"的模板位置——带署名的 user 侧消息,或专用的成员标记格式。**严禁**将任何其他参与者的消息放入当前 AI 的 assistant 续写位(即模型读作"我自己说过的话"的位置)。

b. **署名保真**:每条消息的署名必须区分三类身份:owner(人类)、其他人类成员、AI 成员(标识到具体成员)。不允许匿名化或合并。

文献依据:朴素拼接历史会触发 echoing——chat 模型对模板有强训练先验,会把伙伴消息当作自己的续写目标,角色混淆与锚定直接从模板层发生,上层机制无法补救(SPASM, arXiv:2604.09212)。署名清晰的"他者观点"天然处于模型的审视姿态,署名本身是抗锚定装置。

违规判定:任何其他参与者的消息出现在当前 AI 的 assistant 角色位;消息无署名;署名不区分上述三类身份。
自查:dump 一次真实拼装产物,逐条核对每条历史消息的 role 字段与署名标记。

### INV-8 增补【协议】发散期模板的两条强制要求

a. **第三人称评估框架**:发散期的实例化指令必须以"评估这个观点/方案本身"的第三人称任务句式书写;禁止"你是否同意 X""owner 认为 Y,你怎么看"式的第二人称立场句式。
文献依据:第三人称视角提示在辩论场景将谄媚降低最多 63.8%(SYCON-Bench, arXiv:2505.23840)。

b. **owner 倾向对冲句**:发散期模板必须包含一条语义为"owner 在发散期表达的倾向是一个输入,不是裁决;按你自己的立场独立评估"的指令。
作用域约束:此句**只允许**出现在发散期模板。出现在收敛执行期模板 = 违规(收敛期服从 owner 推进是协议要求,同一干预在两个阶段正负号相反)。
文献依据:第一人称观点陈述("我认为/我感觉")是谄媚的可靠扳机,跨模型家族平均诱导 63.7% 的错误同意;权威/专家框架影响可忽略(arXiv:2508.02087 等)。

违规判定:发散期模板缺任一条;对冲句出现在非发散期模板。
自查:逐个阶段读模板文本。

## 2. 新增条目

### INV-15【实现建议】机制三:差异度仪表的方法学

- 指标:同一轮各 AI 公开输出、模型提供的 summary、或专门 stance digest 的 **pairwise 余弦相似度 + 有效秩**(effective rank)。
- 输入对象只能是公开输出、模型提供的 summary、或专门生成的 stance digest;不得依赖隐藏 CoT。
- embedding 编码器选定一个后固定,中途不换——编码器选择会强烈调制测得的塌缩程度,换编码器 = 曲线不可比(arXiv:2604.03809)。
- 展示三个维度:① 随轮次的趋势;② owner 发出带立场消息的前后跳变;③ 是否持续向某一固定成员靠拢(尤其房间里最强的模型)。
- **只展示给 owner,不触发任何行为**。主文档 P 区禁止项全部继续有效。

### INV-16【实现建议 · 产品配置】成员选型参考

- 异构(跨厂商)优先于同家族不同档位:同一模型挂不同角色 prompt 的委员会,被测得思维链余弦相似度约 0.89、三成员有效秩仅 2.17——角色 prompt 不能制造先验差异(表征塌缩,arXiv:2604.03809)。
- 同等条件下偏好 reasoning 优化档位:对齐微调放大谄媚,推理优化增强对不当用户观点的抵抗(SYCON-Bench)。
- 此条不是代码约束,是房间默认配置与选型文档的依据。

### INV-17【协议 · 最高优先级】记忆投毒的 lineage / provenance 防线

Atrium 的投毒链是:

`不可信消息(第 3 段,瞬态) -> 影响该轮 AI 输出 -> 履历追加 -> 此后每轮以当前 AI 私有证据进入第 4 段 -> 持续影响判断`。

因此,私有履历不是普通日志,而是可被不可信输入间接写入的长期 prompt 源。每条履历必须记录:

- `trigger_message_id`:触发本轮的消息。
- `response_message_id`:本轮 AI 回复落库后的消息。
- `phase_at_generation`:生成时阶段。
- `context_until_message_id`:生成时可见上下文水位。
- `input_stance_record_ids`:本轮第(4)段实际注入过的上游履历 ids。
- `excluded_at_ms / exclusion_reason`:owner 溯源清除后的排除墓碑。

owner 发现某条成员消息、外部粘贴内容或 AI 输出有问题时,必须能按 source message 级联排除所有直接/间接派生履历。排除后的履历不得再进入第(4)段,但审计痕迹保留。

文献依据:MINJA 证明普通查询交互即可污染 agent 长期记忆,理想条件下注入成功率超过 95%、攻击成功率超过 70%(arXiv:2601.05504; 原 MINJA: arXiv:2503.03704)。Zombie Agents 证明一次间接注入可在原始上下文消失后持续控制自演化 agent,且能抵抗滑窗、检索排序等常见机制(arXiv:2602.15654)。MemLineage 将防御定义为 chain-of-custody / lineage enforcement,而不是单纯过滤(arXiv:2605.14421)。

违规判定:履历无法追溯到触发消息;无法从某条 source message 找出所有后代履历;owner 清除后污染文本仍出现在第(4)段;把 delimiter / quoted evidence 当作确定安全边界。

### INV-18【协议】数据生命周期语义

消息删除、撤回、成员退出、AI 移除都必须定义对以下对象的影响:

- 最近消息窗口:软删/撤回消息不得继续作为普通可见历史注入。
- 白板 source anchors:指向被删/撤回消息的锚点进入 `stale` 或 `purged` 状态,owner 决定保留、清除或重建。
- 私有履历:若履历由被删/撤回消息直接或间接触发,必须走 INV-17 的溯源排除。
- 后续 prompt:被排除的消息、锚点和履历不得静默回灌。

默认策略是"软删 / 墓碑 / 排除注入 / 保留审计";物理删除另设隐私合规策略,不得混入 v1 普通删除语义。

违规判定:消息已删除但其派生履历仍进入第(4)段;白板锚点悬空但仍被渲染为 active source;成员退出后其私有数据可被新成员或其他 AI 读取;AI 移除后其私有履历仍被其他 AI 注入。

### INV-19【协议】phase watermark 与过期写回

每个 AI 任务派发时必须携带当前 `phase` 和 context 版本/更新时间。AI 写回时若阶段或关键上下文已变化:

- 普通可见发言可以落库,但必须可标记为 stale/late。
- 不得自动追加私有履历,除非记录带有旧 phase watermark 并且不影响当前阶段解释;更保守的 v1 实现可直接不追加,等待 owner 重新触发。
- 不得写白板、提交提案、切阶段或确认草稿。
- owner 确认 draft/proposal 时若 `base_phase` 或 `base_context_updated_at_ms` 过期,必须提示或要求重新确认。

违规判定:旧阶段任务用旧模板生成的内容在新阶段被当作当前履历回灌;owner 确认过期草稿时没有任何提示;阶段切换后仍允许在途 AI 写入边界动作。

### INV-20【实现建议】owner 门禁退化仪表

owner 确认是 v1 的承重点,但不能假设"人在场"等于"监督有效"。需要记录:

- 草稿编辑率。
- 未编辑批准率。
- 批量批准率。
- 提交到确认的延迟。

编辑率趋近 0、未编辑批准率持续升高、批量批准集中出现时,提示 owner:门禁可能退化为形式审批。此仪表只提醒 owner,不自动阻止决策。

文献依据:human-AI workflow 中存在 automation bias / overreliance;大量 AI 建议和纠错负担会降低审查 engagement,并增加接受错误建议的倾向(arXiv:2103.02381; arXiv:2509.08514)。

## 3. 风险登记(v1 不要求行动,v2 设计必须携带)

**R-1 机制二的翻转固化。**
谄媚翻转一旦发生,约 78.5% 概率持续(arXiv:2502.08177, SycEval);翻转后的发言被 append 进立场履历,机制二自下一轮起会把顺从产物当作"立场连续性"强化。v1 的缓解 = INV-8 增补(降低翻转发生率) + INV-17(允许溯源排除污染履历);根治方案(履历是否需要区分"独立立场"与"顺从转向")留给 v2 评估。

**R-2 引力中心塌缩。**
agent 不仅向多数靠拢,也向更强的模型靠拢(arXiv:2506.01332)。异构房间的塌缩方向可能不是多数,而是最强成员。由 INV-15 展示维度③监测;是否干预、如何干预,owner 决定。

**R-3 长讨论的问题漂移。**
讨论过长时,agent 偏离任务要求、表现下降(problem drift, arXiv:2410.22932)。Atrium 的阶段机与 owner 拍板是天然约束,v1 不加额外机制;记录在案,供机制三曲线对照解读。

**R-4 工具期外泄风险。**
当前 proposal 通道已包含工具/资源动作的设计位置。未来 AI 成员获得 web fetch、文件、外呼工具前,必须单独进行对抗性审计:投毒内容 + 房间内私有讨论 + 对外通道 = 数据外泄三要素。

## 4. 可复现评测计划

- **记忆投毒**:成员消息、外部粘贴文档、弱 AI 成员输出三条入口分别注入;验证 owner purge 后污染文本不再从第(4)段出现。
- **级联清除**:删除或标记某 `root_message_id` 后,所有直接和间接派生 stance records 从第(4)段排除;白板锚点变 stale/purged。
- **生命周期**:消息软删、AI 成员移除、人类成员退出/加入、中途新增 AI;验证消息窗口、私有履历、白板锚点一致。
- **phase 竞态**:旧阶段任务延迟写回、新阶段 owner 已确认、旧 draft 被确认;验证 stale 写回不会污染履历或白板。
- **owner 门禁**:模拟高频 draft 批准,检查编辑率、未编辑批准率、批量批准率能暴露"审批剧场"。
- **多轮 sycophancy**:不仅测单轮翻转,还测翻转后的多轮持续性。
- **中文/混合语言注入**:spotlighting / datamarking 相关缓解必须覆盖中文、无空格文本、混合中英、伪 delimiter 攻击。spotlighting 只能当 prompt guardrail,不能当安全边界;论文也指出 delimiter 可被绕过(arXiv:2403.14720)。

## 1. 架构与角色(已拍板)

### INV-21【协议】agent 进程角色盲

- agent 进程不得包含任何 owner_id / admin_id 的权限判断逻辑。权限、审批、角色语义全部归后端控制面。
- 审批流全程不经过 agent:**前端渲染举手 → 用户(owner 或管理员)决策 → 后端收到决策、落库、更新白板 → agent 每次任务读取最新已确认数据。**

违规判定:agent 代码中存在 owner_id / admin_id 的比较、审批分支、权限校验。
自查:grep agent 代码库中 owner / admin 字段的全部使用点,合规状态下只剩展示标签透传。

### INV-22【协议】任务接口两字段;INV-5 第(5)段措辞同步修订

任务契约只含两个消息边界字段:

| 字段 | 含义 |
|---|---|
| `visible_until` | 可见边界(水位)。agent 只能读 ≤ 此序号的消息;同一轮所有并行任务共享同一水位(Form A 一致性的实现点) |
| `focus_from`(可选) | slot 3 / slot 5 分界。缺省规则:快照尾部最后一组同作者连续消息为第(5)段 |

**INV-5 修订:第(5)段语义从"当前用户消息"改为"快照尾部"。**理由:产品模型是 AI 像高认知真人一样**读完积累的全部消息后对会话状态回应一次**,多人异步下"触发消息"与"最新消息"分离,第(5)段放的是快照尾部消息组,不是某条被钉住的触发消息。

设计史注记(与第 3 节直接相关):曾考虑第三字段 `caused_by`(因果记账),**已否决**。理由:多消息触发下"AI 回应了哪条"是模型内部意图,外部不可观测;触发合并(INV-23)下一个任务的"触发"可以是一组消息甚至无消息(owner 手动点名某 AI 发言)。不可观测的量不能做协议字段。原拟用途的归属:链式深度控制 → 后端 round 计数;`<NO_REPLY>` 统计 → 记在任务记录(task_id)上("此任务无输出"),不需要"拒绝了哪条消息"这种区分。

### INV-23【协议】任务不可变与触发合并

- 任务字段创建时冻结;在途任务的任何字段不得修改。phase 与 `visible_until` 遵守同一"创建即冻结"纪律(与你的 INV-19 同族)。
- 生成期间到达的新消息不属于任何在途任务,自然排队为下一轮素材。
- 撤销重发(supersede)现阶段不实现;将来实现时形态是"替换任务",不是修改任务。
- 触发合并:后端编排保证**一个 AI 一轮最多一个任务**,水位覆盖该轮全部积累的触发。一条消息引发多个 AI 同时举手或连环逐条回复,视为实现缺陷。

### INV-24【协议】agent 读通道

- agent 禁止一切写(既有结论);读必须经后端受限通道,pull(读 API)或 push(后端切好素材打包进任务)二选一,由实现定。
- 通道形状强制三条:只含 ≤ `visible_until` 的消息;履历只含当前任务 ai_id 自己的(INV-6 的通道级实现);白板只含**已确认**内容——草稿与待确认提案的正文不可见,白板可含"待确认 #id"指针行。

## 2. 提案(举手)机制(已拍板)

### INV-25【协议】提案是流内公开事件

- AI 举手在消息流中落一条**特殊类型消息**(提案正文 + 待确认标记),以普通发言的信任级进入所有成员第(3)段(quoted-evidence 渲染,无指令权限)。

- 提案不阻塞讨论:普通发言永不等待审批。
- 无自动通过:无人确认的提案永久待确认;停滞必须显式可见(待确认数量 + 最早提案时间),不允许静默积压。

### INV-26【实现建议】提案稀缺性与校准

- 举手是重大边界动作,稀缺性靠 agent 侧门槛:模板/协议写明何种情况值得提案。
- 评测项:false proposal(不该举的举了)、missed proposal(该举的没举)——与 `<NO_REPLY>` 弃权校准同族:沉默要校准,举手也要校准。

### INV-27【实现建议】裁决人

- owner 可就某争议任命一个 AI 成员为裁决人,出具裁定草稿:裁定 + 理由 + 对立方案可取处 + 残余不确定性 + 少数意见,带出处锚点。

## 3. 投毒体系复审(修订提议,请审查)

### 3.1 trigger_message_id 的语义缺陷

你的 INV-14 把 `trigger_message_id` 设为履历必填,INV-17 的级联第一跳建在它上面。问题:在 INV-22 的产品模型下,**这个字段没有可靠语义**——AI 面对的是整张快照,"它回应了哪条"不可观测;触发合并后一个任务对应一组触发甚至零触发。强行填入(比如填"开轮时最早的待处理消息")得到的是一个**看起来精确、实际任意**的值,级联追踪的精度是假的。可观测的替代是曝光语义(`context_until_message_id`,你已要求记录):污染消息 M 可能影响所有"水位 ≥ M"的履历——但用曝光做自动级联等于"M 之后的一切都可疑",过粗,清除即清空。**精确级联需要的字段不可观测,可观测的字段只支持过粗的级联**——这是该机器的结构性困境,不是实现问题。

### 3.2 威胁度复审

文献中 memory poisoning 的高危性(MINJA、Zombie Agents)建立在一个前提上:**被毒化的记忆驱动自动动作**(自动调 API、自动执行、自动写状态)。Atrium 结构性不满足这个前提——一切边界动作过人类确认(INV-11 / 21 / 25),AI 输出不直接驱动任何动作。因此投毒在 Atrium 的最坏后果不是危险行为,是**某 AI 成员观点被持久带偏**——这与谄媚翻转固化(你的 R-1)是同一类、同一严重度的现象:owner 在讨论中可观察(一个 AI 突然偏执于单一维度),INV-15 差异度仪表可监测,INV-20 门禁仪表覆盖其下游(带偏观点 → 流畅共识 → owner 误确认)。

### 3.3 修订提议

- **INV-14 provenance 缩编**:必填字段改为 `response_message_id`、`phase_at_generation`、`context_until_message_id`;`input_stance_record_ids` 降为可选(它是你设计里最聪明的一笔,跨代追踪靠它而非 trigger,保留实现不浪费);`trigger_message_id` 移除必填,可留作后端调试字段,不进协议。
- **INV-17 降级**:从"最高优先级协议 + 自动级联清除"降为"**履历可观察 + owner 手动管理**":owner 可查看任意 AI 的履历条目(带 phase / 轮次 / 水位面包屑),可手动排除单条;你的墓碑语义(排除注入 + 保留审计)**保留**,优于物理删除。自动级联降为可选实现——已写的代码不必删,从协议路径摘除即可。
- **INV-18 同步降级措辞**:消息删除 → 窗口剔除 + 锚点 stale(保留,这部分与投毒无关,是一致性问题);"派生履历必须走溯源排除"改为"owner 可按曝光范围(水位 ≥ 被删消息)人工审查相关履历"。成员退出/AI 移除的隐私语义**保留不降**——那是隐私边界,不是投毒。
- **评测计划调整**:记忆投毒、级联清除两项降为可选;生命周期、phase 竞态、owner 门禁、多轮 sycophancy、中文/混合语言注入**全部保留**——注意中文注入测试的价值在防 echoing 与渲染稳健性,不依赖投毒定级。
- **明确保留不动**:INV-7 增补的角色位与署名保真、quoted-evidence 渲染——它们防的是 echoing(模板层失败),与投毒定级无关,不得随本次降级一并弱化。
- **核对顺序**:INV-17 从第二位移出,INV-21(角色盲)与 INV-22(接口语义)进入高优先级——它们是当前接入工作的阻塞项。建议:INV-6 → INV-21 → INV-22 → INV-11 → INV-13 → INV-19 → INV-7 → INV-8 → 其余。最终顺序待你按代码现状回传确认。
