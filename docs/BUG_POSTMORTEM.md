# 疑难排查

记录 Atrium 开发中两个排查耗时最长的 bug。不是线上事故——两个都是在压测和调试中发现的，排查过程本身值得记下来。

---

## 一、定时器堆超时队列残留导致空指针崩溃

### 现象

服务在跑 42 接口的批量压测脚本时崩溃。ASan 指出崩溃在 `closeNow()` 里——它拿一个 fd 去连接表里取连接对象,取到的是空的,解引用就崩了。

奇怪的地方在复现条件:

- 单个接口 `-c 100` 一直压,不崩。
- 42 接口脚本 `-c 20`,不崩。
- 只有 42 接口脚本 `-c 100` 会崩,而且比较稳定。

(这里的"42 接口脚本"和"单接口"不是两种不同的测试,都是 oha。脚本只是把 42 个 oha 串起来跑、中间穿插火焰图采集;单接口就是手动一条条敲 oha。区别只在跑了多少轮、怎么编排。)

崩溃不挑具体接口,42 个接口换着崩,说明根因和某个接口的业务逻辑无关。它只在"接口多、并发高"时出现,这个特征当时没法马上解释,但它是后面排查的主要线索。

### 排查

排查从最直接的地方开始:`closeNow()` 为什么会拿到一个已经不存在的连接。`closeNow()` 有多个调用点,崩的这次来自定时器超时路径——定时器取出一个 fd 交给 `closeNow()`,而这个 fd 的连接早就没了。

一开始怀疑过定时器堆有没有把已关闭的 fd 漏在里面没删,也怀疑过多个 Reactor 之间会不会对同一个 fd 有竞争。前者很快否掉:正常关闭路径里 `closeNow()` 是会调 `remove(fd)` 清定时器的。后者也否掉:每个 fd 在生命周期内只属于一个 SubReactor,连接表是各 Reactor 私有的,跨 Reactor 的操作都走 eventfd + 任务队列投递,由目标 Reactor 在自己线程里处理,不存在跨线程抢同一个 fd。

排到这里矛盾变得很具体:单 Reactor 内是串行执行的,一个 fd 被关闭时,它的所有东西——包括它在定时器堆里的登记——本该一起清掉。那 `closeNow()` 怎么还会拿到一个已经清掉的 fd?

除非,有一条路径把这个 fd 的"待处理"记录存到了某个地方,而关闭流程没清到那个地方。顺着这个问题去看定时器堆的内部结构,根因就在那里。

### 根因

定时器堆内部有两份数据:

- 主索引:最小堆 + 一个 `fd → 堆内下标` 的映射,管所有在监视中的连接。
- `m_expired` 数组:一个"已经超时、等待处理"的暂存区。

它的运作方式是:`tick()` 扫主索引,把超时的 fd **从主索引里移出来**,追加进 `m_expired`;事件循环要等到 `epoll_wait` 这一轮没有事件返回(空转)时,才调 `getExpired()` 把 `m_expired` 里的 fd 取出来集中处理。

关键点是中间这个"移出来":一个 fd 一旦被 `tick()` 判超时,它就**离开了主索引,只待在 `m_expired` 里**,等一个之后才会到来的处理时机。

而连接正常关闭走 `closeNow()` 时,会调 `remove(fd)` 去清定时器登记。`remove(fd)` 清的是**主索引**——它按 fd 在主索引里查找、删除。如果这个 fd 此前已经被 `tick()` 判超时、移进了 `m_expired`,那 `remove(fd)` 在主索引里**根本找不到它**,也就清不到 `m_expired` 里那条记录。

`m_expired` 因此成了一块清理逻辑覆盖不到的地方。fd 进了它,就脱离了主索引,而所有清理(包括 `remove`)都是冲着主索引去的。没有任何一条路径,能在"连接还没被 `getExpired()` 消费、就先关闭了"的时候,把它从 `m_expired` 里撤回来。

完整的崩溃链:

1. 某连接被判超时,`tick()` 把它的 fd 移出主索引、推进 `m_expired`,等待处理。
2. 在被处理之前,这条连接因为别的原因关闭了,走 `closeNow()`。`closeNow()` 调 `remove(fd)`——主索引里已经没有这个 fd,清理是空操作;连接对象被移出连接表,fd 被 `close()`。
3. `m_expired` 里那条记录成了孤儿:连接没了、fd 关了、主索引里也没有,只有 `m_expired` 还攥着它。
4. 之后某次 `epoll_wait` 空转,`getExpired()` 把这条孤儿 fd 取出来交给 `closeNow()`。`closeNow()` 拿这个 fd 去连接表里取连接——取到一个不存在的键,得到空对象——解引用,崩。

### 为什么是"42 接口 -c 100"才崩

崩溃链要凑齐,需要一个 fd **先**超时进了 `m_expired`,**又**在被处理之前关闭。

连接的超时时间在它收到数据时会刷新,所以一条在正常收发的连接不会超时。要被判超时,连接得真的空闲够久。压测里这种空闲出现在一个具体位置:oha 以 `-c 100` 启动时,100 条连接是陆续建立的,服务端每 accept 一条就登记进定时器堆、超时开始计时。但 oha 不会在同一瞬间给 100 条连接都发出第一个请求——在 2 vCPU / 2 GB 这种处理能力下,排在后面的连接,可能在"连接已建立、已登记、但还没收到第一个请求"的状态下停留比较久。这段停留如果超过超时阈值,这条连接就会在从没收发过任何数据的情况下被判超时,进 `m_expired`。之后压测正常进行,`epoll` 一直有事件,`m_expired` 一直积压不被处理;直到 oha 的 `-z 30s` 到点退出,连接被集中关闭,凑齐了崩溃链后面几步。

**需要说明的是:上面这套"为什么触发"的机制,是通读相关代码后推演出来的,没有做针对性的复现实验去验证它。** 实测能确定的只有:42 接口 `-c 100` 稳定崩,单接口和 42 接口 `-c 20` 在试过的多轮里没崩过。但"多轮没崩"不足以说明单接口结构上不会崩——这是个时序竞态,触发取决于有没有连接恰好落进那个窗口,42 接口脚本是几十轮独立压测的累积,把单轮的低概率放大成了稳定复现;单接口轮次少,只是没撞上。常规 keep-alive 压测连接全程活跃、不会空闲超时,日常使用也一样,所以都碰不到。

### 修复

两层,是兜底关系不是重复:

- `remove(fd)` 除了清主索引,也去 `m_expired` 里查一遍、删掉。这样连接关闭时,不管它此刻在主索引还是已经进了 `m_expired`,都能清到。
- `closeNow()` 入口先检查 fd 在不在连接表里,不在就直接返回。就算以后再出现类似的孤儿记录漏到这一步,也只是被安全忽略,不会解引用空对象。

修复后跑 42 接口 `-c 100` 全脚本三遍,零崩溃。

### 反思

`m_expired` 这个中间状态从设计之初就没被纳入统一的清理逻辑——当初默认了"进来的 fd 很快会被处理掉",没考虑处理之前连接可能因为别的原因先没了。一个中间状态只要被多条路径碰,就得明确谁负责在它失效时清它,否则每加一条新路径都是一次踩坑的机会。

## 二、日志重载选错导致一行日志从不输出

### 现象

排查一次 AI 调用失败时,要看 `ai_client.cpp` 里一条记录响应详情的 `LOG_DEBUG`。结果发现这行日志在几万行历史日志里一次都没出现过。

但它看起来必然会执行:上一行 `LOG_DEBUG` 正常输出;它和上一行之间只隔一句 `if (!res) return;`;它后面那个 `switch` 的结果还确实出现在了另一条 WARN 日志里——说明代码确实跑过了这一行所在的位置。前面执行了,后面也执行了,中间这行没有分支、没有返回的直线代码,就是不输出。

### 排查

先排表层的:`strings` 确认二进制里有这行的格式字符串、确认日志级别是 DEBUG、确认同一个函数里别的 DEBUG 行正常输出、重新编译重启后还是这样。

`grep -c` 数前后两行日志的出现次数,把范围锁死在这两行之间。然后做拆分:在问题行正上方加一行没有参数的 `LOG_DEBUG("MARKER")`——MARKER 正常输出,说明代码确实走到了问题行的正上方。再把问题行按格式串里的占位符拆开——只有一个 `%d` 时正常,只有一个 `%s` 时正常,但 `%d` 和 `%s` 同时在的时候,整行输出就不对了。

排查中间走过一段弯路,有一个结论说是 `vsnprintf` 处理 `%d` + `%s` 时把调用栈破坏了。这个结论是错的,被否掉了——标准用法的 `vsnprintf` 不会破坏调用者的栈,这只是一时解释不了现象时的兜底猜测。一个跟语言规则相矛盾的结论,听着再像回事也得丢掉。

接着把 logger 从 server 这个复杂环境里单独拎出来,只编译 logger 相关的几个文件做最小复现;又把 `logf` 的核心逻辑手抄成一个独立函数单独测——结果都正常。这说明 `vsnprintf` + 变参的写法本身没问题,问题出在真正的 `logf` 所在的环境,不在它自己的实现里。

最后一步是让编译器自己讲:在两个 `logf` 重载的函数体里各加一句打印自己签名的语句。一跑,终端打出来的是四参重载的签名——根因当场就清楚了。

### 根因

`AsyncLogger::logf` 有两个重载:

```cpp
logf(LOGLEVEL level, const char* fmt, ...);
logf(LOGLEVEL level, const char* file, int line, const char* fmt, ...);
```

调 `logf(DEBUG, "...%d...%s", a, b)` 时,格式串后面正好跟两个参数。对这两个重载来说,这个调用都能成立:

- 三参重载:`fmt` 接格式串,`a`、`b` 由 `...` 接。
- 四参重载:`file` 接格式串,`line` 接 `a`,`fmt` 接 `b`,`...` 为空。

C++ 重载决议里,靠 `...` 接收的参数算较差的匹配。四参重载用具名形参精确接住了更多参数,被判成更优。于是编译器选了四参重载——格式串被当成 `file`,第一个数据参数被当成 `line`,第二个数据参数被当成了真正的 `fmt`。`vsnprintf` 拿一个普通数据参数当格式串解析,输出就乱了。它不报错、不警告、不崩溃,只是静默地选错。

"只有 `%d` + `%s` 才出问题"是个假象。真正的条件是:格式串后面跟的参数个数,恰好让四参重载也能成立。绝大多数 `LOG_DEBUG` 调用因为参数个数凑不齐四参重载的形参,只能匹配三参重载,正常工作;只有"格式串 + 正好两个参数"这种形态会中招。

### 修复

删掉多余的四参重载——没有任何调用方真的按四参形式用它。`logf` 只剩一个签名后,重载决议没得选,问题消失。之后按惯例把日志级别的宏统一改成带 `file:line`。

### 反思

这个 bug 暴露的是 C++ 变参函数参与重载决议时一个反直觉的点:`...` 的"较差匹配"特性,会让一个看着没问题的重载在特定参数个数下悄悄把调用截走,而且编译期运行期都不给任何提示。比根因更值得记下来的是排查里两个判断:一是当一行直线代码稳定不输出时,该怀疑的不是"它为什么不执行",而是"它是不是我以为的那行代码"——这里它执行了,只是执行的不是预期的那个重载;二是要丢掉听着专业但跟原理矛盾的结论,"`vsnprintf` 破坏栈"就是这种。

## 两个 bug 的共同点

根因完全不同,但排查走的是同一条路:

- 从"不该发生"的现象出发,把那个矛盾点抓住不放——直线代码不输出、单接口不复现,这种反直觉的现象本身就是最强的线索,它说明某个默认成立的假设其实不成立。
- 从最直接的地方开始查,矛盾排不掉就往里走一层。
- 隔离 + 最小复现,用来区分"实现错了"还是"环境/调用方错了"。
- 推理卡住时,不要继续在纸上推,加一句打印让程序在运行时自己说它干了什么。一个运行时事实,比十个假设管用。

两个 bug 共享同一类根因:一个被多方共享的东西(`m_expired` 暂存区、`logf` 的重载集合),它的行为边界是隐式的——没人明确写过"expired 里的 fd 可能被提前关闭"、"格式串后恰好两个参数会走错重载"。新加的路径很自然就踩了进去。这类 bug 的共性不是代码写错了,是代码没写出来的假设本身就是错的。
